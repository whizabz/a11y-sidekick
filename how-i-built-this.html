Phase 1

Concept & Architecture

Defining the problem, deciding what to build, and committing to a deliberately minimal stack.

01 Idea

The problem with accessibility checklists

Most WCAG checklists hand you all 55 criteria at once and leave you to figure out which ones apply. If you're reviewing a simple marketing page, you don't need the media captioning criteria. If your screen has no form fields, half the Design → Dev criteria are irrelevant. I wanted a tool that filters the list down to only what's actually relevant for a given screen — and organises it by who on the team is responsible for fixing each thing.

WCAG 2.2 Design tools A11y
02 Decision

Single HTML file — zero dependencies

I made a deliberate call early: this would be one HTML file with everything inline. No npm, no build step, no framework. A designer can open it directly in a browser or serve it with a single Python command. The lack of dependencies means it never breaks — no packages to go stale, nothing to update. The only external dependency is Google Fonts, which degrades gracefully if it fails.

Architecture Vanilla JS No build
03 Prompt

Writing the spec before touching code

Before starting the build I wrote a detailed spec: the full CRITERIA data model, the three-layer filter system, all 55 criteria with their triggers mapped out, and the checklist UI behaviour. Having this as a reference document made the actual build much faster — the AI had a single source of truth to work from rather than needing me to re-explain the domain model in every prompt.

Spec-first Data model

Phase 2

Core Build

Building the CRITERIA data array, filter logic, checklist renderer, and the full WCAG reference tab from the spec.

04 Prompt

The CRITERIA array — 55 objects, all inline

I asked Claude to build the full CRITERIA array from the spec. Each criterion is a plain JS object with an ID, title, layer, role, trigger list, rule text, Do/Don't text, and optional extras — a doc note for Design→Dev handoff, an impl note for Dev, an owns note for Content. The array lives directly in the script tag. About 1,500 lines of structured data that needed to be accurate; working from the spec as source of truth kept it clean.

CRITERIA array Data
05 Decision

Three-layer filter model

The filtering works in three layers: always-on criteria are included regardless of what's selected; structure criteria fire on layout properties of the screen (sticky headers, overlays, timeouts); element criteria fire on what UI components are present. A criterion can appear in multiple trigger lists — if the user selects both "Has overlay" and "Form field", a criterion that responds to both only appears once. Deduplication is by WCAG ID, not by position in the array.

Filter logic Deduplication Layers
06 Prompt

Checklist renderer — state management and role grouping

The renderChecklist() function groups filtered criteria by who owns them: Design, Design → Dev, Dev Only, Content. Always-on criteria distribute into their role group. The ✓ and NA toggle states are stored in a Map keyed by criterion ID — clicking an already-active state button toggles back to open. Crucially, this Map persists across regenerations, so if you update your selections, checked items stay checked for any criterion that's still in the new list.

renderChecklist State Map Role grouping
07 Prompt

WCAG by Role reference tab

The second mode came from an existing wcag-guidelines.html file that already had all the reference content built out. I wrapped it in the new tab system and preserved the POUR-section structure (Perceivable / Operable / Understandable / Robust) within each role tab. The label "Full Reference" got renamed to "WCAG by Role" later — it says both what standard it covers and how it's organised, which is more useful at a glance.

Reference tab POUR Static HTML

Phase 3

Form Redesign

Rethinking the selection flow so the experience of building a checklist felt more intentional and less cluttered.

08 Pivot

The always-on callout was in the wrong place

The original layout showed the always-on criteria list first, then the structure chips, then the element chips. This felt backwards — the always-on list is informational, not something the user configures. I moved the selections to the front so the form reads: name the screen → pick structure → pick elements → generate. The always-on callout moved below the generate button, since it describes what's automatically included rather than what the user is choosing.

Form UX Information order
09 Prompt

Chips inside the card border, Reset per group

Two changes at once: the selection group titles were straddling the card border (a default fieldset/legend behaviour that's hard to override cross-browser), so I switched to div + role="group" + aria-labelledby for full layout control. I also replaced the single global Clear button with individual Reset buttons inside each group header — so you can clear structure selections without losing your element picks and vice versa.

fieldset → div aria-labelledby Per-group reset
10 Prompt

Collapsing the form after generation

Once you generate a checklist, you don't need the full form occupying the top of the page. I added a collapsed state that replaced the expanded form with a compact summary — screen name, the selected filter chips, and an Edit button. This later got replaced entirely by an edit modal (the summary card created duplicate chips once the progress card also showed selections), but the idea of hiding the form after generation was right.

Form state Collapsed UI

Phase 4

Checklist UX

Making the generated checklist faster to work through — role tabs, trigger filters, and a tighter progress model.

11 Prompt

Role tabs replace static section headers

The first checklist version stacked all role sections one after another with static headers. For a complex screen this could mean 30+ criteria in a long scroll. I replaced the headers with a segmented nav — Design, Design → Dev, Dev Only, Content — so you can jump between roles without scrolling. Each tab shows the criteria count. The "All" option was dropped early on; defaulting to Design made more sense since that's usually the first person reviewing the screen.

Segmented nav Role tabs
12 Prompt

Trigger filter chips — the key UX insight

A designer reviewing a screen with six selected elements might want to focus specifically on everything related to "Form field" — work through all the form field criteria in one go, then move on. There was no way to do that. I added trigger filter chips inside the progress card, one per selection the user made. Clicking "Form field" narrows the visible criteria to only those triggered by form fields, with role tab counts updating live. Each criterion card also shows which of your selections triggered it as small chips in its metadata row.

Trigger filter Criterion chips Focused review
13 Decision

Always show Do/Don't — drop the guidance toggle

The original design had a "Show guidance" toggle that expanded the Do/Don't blocks. The thinking was to keep cards scannable. In practice the guidance is the whole point — when you're checking a criterion you want to know immediately what "done" looks like. Removing the toggle made each card self-contained with no extra interaction needed. It made the page longer, but each card became more immediately useful.

Remove friction Information density
14 Decision

X/Y Done — N/A reduces the denominator

Replacing "30 total criteria" with "X/Y Done" was the easy part. The interesting decision was what Y should be. If you mark 5 items as N/A they're not things you need to review, so they shouldn't inflate the denominator. Y = total minus N/A items. This means your progress counter reflects actual reviewable work rather than a raw count that includes things you've already decided don't apply. I also removed the progress bar and the done/N/A/open stat chips to keep the progress card compact.

Progress model N/A denominator

Phase 5

Edit Modal & Hierarchy

Replacing the collapsed summary card with a dialog modal — and untangling a stubborn mobile CSS bug.

15 Pivot

The summary card was duplicating the chips

After adding trigger filter chips inside the progress card, the selections were showing up in two places at once: the collapsed summary card at the top of the page AND the progress card below it. The hierarchy wasn't making sense. The fix was to remove the summary card entirely — the progress card already showed the screen name and selections. Editing moved into a dialog modal triggered by a small pencil icon in the progress card header.

Hierarchy Remove duplication
16 Prompt

Building the edit dialog

I replaced the Edit button with a native HTML dialog element. Clicking the pencil icon opens it pre-populated with the current screen name and selections. Save & Regenerate reads from the modal inputs, updates the state, and re-renders the checklist while preserving all existing done/N/A states for any criteria that are still in the new list. The browser's built-in dialog handles focus trapping and Escape-to-close natively — no JS needed for that part.

dialog element State preservation Native browser API
17 Debug

Mobile CSS ghost: state-actions { width: 100% }

After moving the ✓/NA buttons to the top-right of each criterion card, they started consuming the full row width on narrower viewports — crushing the meta badges (the criterion code pill and layer tag). The root cause was a leftover mobile media query: .state-actions { width: 100% }. It had been added when the buttons used to stack below the title at small sizes. The card structure changed but the CSS hadn't been cleaned up. Removing that single rule fixed it immediately.

Phase 7

Polish & Handoff

A second iteration pass — tighter visual design, per-chip review, scroll-aware filters, and exports that travel back into Figma.

23 Prompt

Kami design tokens and Phosphor icons

The UI got aligned to the Kami design system — parchment surfaces, ink-blue accent, warm grey text hierarchy, solid tag tints instead of translucent washes. Icons moved to Phosphor via CDN: check and X in Do/Don't blocks, pencil for edit, info for WCAG originals, download for export. The goal was the app feeling like a considered document tool, not a generic form.

Kami Phosphor Visual polish
24 Pivot

Per-chip review instead of whole-card ✓/NA

A criterion triggered by three selections — say Text, Button, and Form field — isn't one binary decision. You might have checked contrast on body text but not on the submit button yet. Whole-card Done/NA was too coarse. Review moved to checkboxes at the bottom of each card, one per matching selection chip. Progress became X/Y Done where Y counts individual chips, not cards. State lives in a triggerStates Map keyed criterionId:trigger, still preserved across regenerations.

triggerStates Per-chip review Progress model
25 Prompt

WCAG original text in a modal

Each checklist card got an info button that opens a <dialog> with the official W3C wording for that criterion — pulled from a WCAG_ORIGINAL lookup table. The app's Do/Don't guidance stays practical and team-specific; the modal is there when someone wants the spec language verbatim without leaving the checklist.

WCAG_ORIGINAL dialog Reference
26 Prompt

Sticky filter bar on scroll

Once you scroll past the progress card, the selection chips disappear — but you still need them to narrow the list. An IntersectionObserver watches the progress card; when it leaves the viewport above, a fixed bar slides in at the top with all structure and element chips in one flat row (no Structure/Elements labels). Same filter behaviour as the progress card; it hides again when you scroll back up.

IntersectionObserver Sticky UI Trigger filter
27 Decision

Export for Figma and CSV

After finishing a review, designers wanted to park the results next to the screen in Figma. Editable HTML-to-Figma paste would need a conversion library; compact plain text works natively — Figma creates a text layer on paste. A download icon on the progress card opens a menu: Copy for Figma (screen name, progress, selections, all roles with ✓/○ per chip) and Download CSV (one row per chip, Excel-friendly with UTF-8 BOM). Both read live state at export time.

Figma handoff CSV Clipboard
28 Prompt

Card layout and header cleanup

Checklist cards were tightened: criterion ID and title on one serif line, layer tag on the right, dividers removed, redundant note lines merged into rule text where they duplicated it. Review chips get a brand-tinted background when checked. Small layout passes like this add up — the checklist reads faster when each card has less visual noise.

Card UX Typography
29 Decision

Remove the dev helper

An "I'm feeling lucky" button had been useful during development — random screen name and chip selections to stress-test the renderer. Once the tool was stable enough to share, it was noise on the form. Removed the button, its CSS, and the randomiser functions. Real workflows start with naming the screen and making deliberate selections.
